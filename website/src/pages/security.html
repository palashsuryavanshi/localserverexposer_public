Security & privacy

What happens when you expose a local server, what the application enforces on your behalf, and where the limits are.

Exposing a server makes it reachable from the public internet. A Quick Tunnel URL is unguessable but bearer access: anyone who obtains it can reach your service until you stop the tunnel. Nothing here turns an unfinished development server into a safe production service.

What happens when you expose a server

Local Server Exposer starts a Cloudflare Quick Tunnel: your local port is bridged to an ephemeral public HTTPS address on *.trycloudflare.com, served through Cloudflare's network.

  • The URL is the credential. The hostname is random, but anyone holding the link can send requests to your service while the tunnel runs.
  • Your server sees real traffic — original paths, headers and body. An unauthenticated admin endpoint on your dev server becomes a public admin endpoint.
  • Cloudflare sees the traffic, as any reverse proxy must. Their terms apply to it.
  • Quick Tunnels are for development. Anonymous, no custom hostname, no account, not a production front end.

Stopping the tunnel ends it: the address stops reaching your machine as soon as the tunnel process exits.

What the application enforces

PropertyHow it works
Confirmation before every exposureA dialog names the port, URL and process. No permanent opt-out.
Only HTTP/HTTPS can be exposedThe app re-probes the target immediately before starting a tunnel and refuses anything that does not answer as a web server — regardless of what the interface says.
Loopback targets onlyDiscovery and probing cover 127.0.0.0/8 and the 0.0.0.0 wildcard. Remote hosts are never probed or exposed.
Tunnels never outlive the appEach tunnel process is attached to a Windows Job Object that terminates its members when the application process ends — including crash, forced kill and sign-out.
No shell executionProcess arguments are fixed and built in the backend. The interface has no shell, filesystem or arbitrary-process capability.
Tunnel client verificationChecked for plausible size, PE executable format and a parseable --version — before first use and again before every tunnel.

Local data and privacy

Everything the application stores lives in %APPDATA%\com.localexp.local-server-exposer\:

ItemContents
config.jsonInterface preferences, favourite ports, scan interval, autostart flag. No credentials.
logs\Daily rotating files with seven-day retention, plus panic.log if the app ever crashes. Tunnel URLs are redacted before writing; response bodies, headers and cookies are never logged.
cloudflared.exeThe tunnel client, present only if you chose to install it, and verified before use.

The application makes no analytics or telemetry calls. Its network activity is limited to the tunnel itself and, once, the tunnel-client download you approve.

One caveat worth stating plainly: Windows toast notifications are kept in the Windows notification history until dismissed, and a tunnel notification includes the public URL. On a shared machine, clear notification history if that matters to you.

Integrity of the download

Every release publishes a SHA256SUMS.txt, and an automated workflow re-downloads the assets and recomputes each checksum after publication, failing if anything does not match.

The binaries are not Authenticode-signed. That means SmartScreen warnings and no publisher reputation; authenticity rests on the published checksum and on downloading only from the releases page.

Known limitations

  • Tunnel URLs are bearer credentials. Inherent to how the model works.
  • No checksum pinning for the tunnel client. Cloudflare publishes no checksum file at the download URL used, so identity rests on HTTPS, file format and the --version output.
  • Self-signed HTTPS origins are reached with TLS verification relaxed, for loopback targets only.
  • No third-party tunnel modes. Named tunnels, custom hostnames and Cloudflare Access are not supported.
  • Local machine only. If your computer is off or disconnected, the public URL stops serving. This is a development tool, not hosting.

What kind of assurance this is

The application has been through an internal threat-model review covering accidental exposure, command injection, path traversal, malicious local services and orphaned tunnels. It has not been penetration tested, audited or certified by an independent third party, and no malware-free status is claimed. A clean antivirus scan on the build machine is a sanity check, not a guarantee.

Reporting a security issue

Report it privately through GitHub Security Advisories rather than in a public issue, and allow the maintainer reasonable time to ship a fix before disclosing details. Never include a live tunnel URL — treat it as a password.
