Getting started

From a running dev server to a URL you can open on your phone, in about a minute.

Before you start

You need a development server that is actually listening, and you need the application to recognise it as an HTTP or HTTPS service. Everything else follows from that.

The app only offers to expose ports that answer HTTP or HTTPS. A database port, a debug protocol or a raw TCP service is shown as Unsupported and cannot be shared — that is a policy decision, not a limitation of the tunnel.

1. Find your server

Start your project the way you normally do, then open Local Server Exposer. The Servers page refreshes on its own every 15 seconds by default; you can also press Refresh.

Each listening port appears as a card showing the port, a clickable local address, and the process that owns it:

ColumnMeaning
:5173The listening port.
http://localhost:5173The address the service is reachable at from your machine.
node.exe · PID 17384The owning process, where Windows lets the app read it.
Status badgeReady, Unsupported, Unknown or Unreachable.

If a port you expect is missing, check that your server binds to 127.0.0.1 rather than a LAN address, and remember that discovery is loopback-only.

2. Expose it

Press Expose on a card marked Ready. A confirmation appears naming the exact URL and process, and stating that the service becomes reachable from the public internet.

  1. Read the dialog

    It names the port, the local URL and the process. Cancel is focused, and Escape or a click outside also cancels.

  2. Confirm

    There is no “don't ask again”. Every exposure and every retry is confirmed individually.

  3. Watch it start

    The card shows Starting while cloudflared registers with Cloudflare. If nothing is published after about a minute, the app fails the tunnel with a reason instead of waiting forever.

3. Share it

When the tunnel is serving, the card shows the public URL with three controls:

ControlEffect
CopyCopies the exact public URL to your clipboard.
OpenOpens the URL in your default browser.
StopStops the tunnel; the URL stops working immediately.

The Tunnels page lists every active tunnel with its URL, status and start time.

4. Stop it

Press Stop on the card, on the Tunnels page, or use Stop all tunnels in the tray menu. Closing the window keeps the app running in the tray; quitting from the tray stops every tunnel.

A tunnel can never outlive the application. If the app is closed, killed, or your machine signs out, the tunnel process is terminated with it — there is no setting that leaves a public URL running unsupervised.

Reading the labels

LabelWhat it means
ReadyAnswers HTTP or HTTPS. The only state that can be exposed.
UnsupportedListening, but not an HTTP service. Cannot be exposed.
UnknownNot classified yet.
UnreachableListed but did not answer the probe — firewalled, closing, or owned by an elevated process.
StartingThe tunnel client is registering with Cloudflare.
ExposedLive. The URL is working.
Stopping…Shutting down.
Tunnel failedIt could not start, or it exited unexpectedly. The card shows why; press Retry.

Finding things quickly

  • Filters — All, HTTP, Exposed, Available.
  • Search — matches port, process name or detected framework.
  • Favorites — star a card to pin it to the top; stored in settings.
  • Unavailable rows — if a tunneled server stops, its card stays visible so you can still stop the tunnel.

Settings worth knowing

SettingEffect
Scan intervalSeconds between scans (5–300).
Enable HTTP / HTTPS detectionOff lists listeners without probing them.
Scan localhost onlyOff lists LAN listeners too, but they are never exposable.
Maximum concurrent probesParallel probes per scan (1–256).
cloudflared executableAutomatic (managed download) or a path you supply. Any copy is verified before each tunnel.
Minimize to trayClosing the window keeps the app in the tray.
Stop tunnel when its server stopsOff (default) keeps a tunnel alive across a quick server restart.
